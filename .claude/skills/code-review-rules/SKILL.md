# 코드 리뷰 규칙

## 순서

1. **기계적 검증** — 사람이 볼 필요 없는 것부터 통과시킨다
2. **공통 규칙** — 스택과 무관하게 사고가 났던 항목
3. **프로젝트 고유 규칙** — `CLAUDE.md` 하네스 설정의 `{설정:고유 규칙}`
4. **스택별 체크** — `stack/` 아래 파일 (`/setup-harness`가 프로젝트에 맞는 것만 복사한다)
5. **테스트** — `test-strategy`의 "리뷰에서 보는 것"
6. **코드 품질 4원칙** — `principles.md`

## 1. 기계적 검증

변경 파일만 대상으로 한다.

```bash
{ git diff --name-only origin/{설정:기본 브랜치}...HEAD; git diff --name-only; git diff --cached --name-only; } \
  | sort -u | grep -E '{설정:소스 확장자}' > "$TMPDIR/changed.txt"
```

- 타입체크: `{설정:타입체크}`
- 린트: `{설정:린트}` (변경 파일만)
- 테스트: `{설정:테스트}`의 관련 테스트

⚠️ 타입에러는 **절대 수치가 아니라 기준선 대비 증가 여부**로 판단한다. 브랜치마다 기존 에러 수가 다르다. 판단이 안 서면 변경분을 stash하고 수치를 재서 비교한다.

⚠️ 린터 출력이 깨지거나 길면 JSON 포매터(`-f json` 등)로 받아 파싱한다.

## 2. 공통 규칙

### 배선까지 확인한다

함수가 존재한다고 동작하는 게 아니다. 다음을 모두 확인한다.

- 호출부가 있는가 — `grep -rn "functionName" <소스 루트>`
- 그 호출부가 있는 화면에 도달 가능한가
- 라우트가 라우터에 등록돼 있는가

설치 경로 추적, 자동 로그아웃 핸들러 등록, 네비게이션 ref 설정 함수가 리팩터링 중 **함수만 남고 호출부가 사라져** 조용히 죽은 적이 있다. 빌드도 타입체크도 통과했다.

### API 타입을 스키마와 대조한다

필드 추가·삭제가 있었는지 `{설정:API 스키마}`와 비교한다. 전체를 읽지 말고 스키마명으로 좁힌다. 서버엔 있는데 타입에 없는 필드가 생기면 기능을 놓친다.

### 기존 컴포넌트·에셋 우선

새 컴포넌트를 만들기 전 `{설정:아키텍처 → 공용 컴포넌트}`를 확인한다.

diff에 아이콘·이미지가 추가됐으면 `{설정:아키텍처 → 아이콘}`에 같은 글리프가 있는지 확인한다. **배경 박스·원·크기만 다르게 해서 새로 만든 것도 중복이다.** 기존 아이콘을 쓰고 배경은 스타일로 감싼다. 반대로 글리프 자체가 다르면 억지로 통일하지 않고 별도 아이콘으로 둔다 (판단이 서지 않으면 개발자에게 묻는다).

```bash
ls <아이콘 디렉터리> | grep -iE "키워드"
```

### 문서 동기화

`{설정:문서 동기화}`에 적힌 짝(예: 라우트 추가 → 화면명 매핑, 이벤트 추가 → 이벤트 문서)을 함께 바꿨는지 확인한다.

## 보고 형식

심각도 순으로 정렬한다. 각 항목에 **파일:줄**과 **구체적 실패 시나리오**를 쓴다.

❌ "동시성 문제가 있을 수 있습니다"
✅ "북마크를 빠르게 두 번 탭하면 두 번째 탭에서 반환값이 초기값으로 나와 토스트가 '제거했어요'로 뜬다"

추측이 아니라 "A 상황에서 B가 된다"로 쓴다. 재현 경로를 못 대면 그 지적은 빼거나 확인이 필요하다고 밝힌다.

지적이 없으면 없다고 말한다. 억지로 만들지 않는다.
