# 검증

검증은 "돌려봤다"가 아니라 **명세 항목마다 증거를 남기는 일**이다. 이 스킬은 무엇을 얼마나 확인할지(레벨), 무엇을 증거로 인정할지, 실패를 어떻게 판정할지를 정한다.

- 화면 캡처 방법 → `ui-verify`
- 테스트 작성 방법 → `test-strategy`
- 명세 항목 분해 → `spec-crosscheck`

## 1. 레벨을 정한다

레벨은 **변경의 크기가 아니라 영향 범위와 위험도**로 정한다. 인증 한 줄 수정이 파일 20개 이름 변경보다 위험하다.

| 레벨 | 대상 | 예 |
|---|---|---|
| **L0 정적** | 로직이 없는 변경 | 문구, 스타일 상수, 에셋 교체, 주석 |
| **L1 컴포넌트** | 한 컴포넌트 안의 UI·로직 | 버튼 상태 추가, 입력 검증 |
| **L2 화면·공용** | 화면 흐름, 여러 곳이 쓰는 코드 | 화면 추가, 공용 컴포넌트·store·API 계층·훅 수정 |
| **L3 전역·고위험** | 앱 전체나 되돌리기 어려운 것 | 라우팅·인증·결제·데이터 삭제·빌드 설정·네이티브 의존성·마이그레이션 |

**한 단계 올리는 경우**

- 결제·인증·개인정보·분석 이벤트를 건드린다
- 사용처가 3곳 이상인 코드를 고친다 (`grep -rn`으로 센다)
- 서버에 쓰기 요청을 보내는 동작이 바뀐다

레벨은 `/feature` 체크포인트 1에서 근거와 함께 제안하고 **개발자가 확정한다.** 구현 중 범위가 커지면 레벨을 다시 제안한다.

## 2. 기준선을 먼저 잰다

변경 전 상태를 기록해야 변경 후 생긴 문제가 이번 변경 때문인지 가를 수 있다.

| 기준선 | 방법 |
|---|---|
| 타입에러 수 | `{설정:타입체크}`의 에러 수 |
| 이미 실패하던 테스트 | `{설정:테스트}` 결과의 실패 목록 |
| 변경 전 화면 | L0 이상이고 UI가 바뀌면 `ui-verify`로 변경 전 캡처 |

브랜치를 만든 직후, 코드를 고치기 전에 잰다. 이미 고쳤다면 `git stash`로 되돌려 잰다.

## 3. 레벨별 필요한 증거

상위 레벨은 하위 레벨의 증거를 모두 포함한다.

| 레벨 | 필요한 증거 |
|---|---|
| **L0** | 타입체크·린트 기준선 대비 증가 없음 + 바뀐 지점의 **전/후 캡처 한 쌍** |
| **L1** | + 통합 테스트(성공 1 + 실패 1, `test-strategy`) + **상태별 캡처**(기본·로딩·빈 데이터·에러 중 해당하는 것) |
| **L2** | + 진입부터 이탈까지 시나리오 검증 + **이어진 기능 회귀**: 사용처마다 최소 L0 증거 + 관련 테스트 전체 실행 |
| **L3** | + E2E 핵심 플로우 + 실서버(스테이징)·실기기 확인 + **되돌리는 방법**(revert 범위, 데이터 복구 여부) |

UI가 바뀌지 않는 변경이면 캡처 대신 테스트·로그를 증거로 쓴다.

### 증거로 인정하는 것

| 증거 | 조건 |
|---|---|
| 테스트 | 테스트 이름이 명세 항목과 대응되고, 이번에 실행해서 통과했다 |
| 캡처 | 바뀐 부분이 화면에 보이고, 비교 대상(시안 또는 변경 전)과 나란히 놓았고, **무엇을 확인했는지 한 줄**이 붙어 있다 |
| 로그·응답 | 해당 동작에서 나온 실제 출력이다 (요청 URL·상태 코드·이벤트명 등) |

**인정하지 않는 것**: "코드상 문제없어 보인다", 이전에 찍은 캡처의 재사용, 실행하지 않은 테스트, 다른 브랜치나 캐시된 빌드에서 나온 결과.

## 4. 판정

항목마다 네 가지 중 하나로 판정한다.

| 판정 | 조건 | 대응 |
|---|---|---|
| ✅ **통과** | 레벨에 필요한 증거가 모두 있다 | — |
| ❌ **실패** | 같은 입력에서 매번 재현된다 | 원인을 찾아 코드를 고친다 |
| ⚠️ **불안정** | 같은 입력인데 결과가 달라진다 | 대기 조건 보강, MSW로 데이터 고정, 시간·랜덤 고정. 그래도 달라지면 통과로 치지 않고 보고한다 |
| ⏸️ **검증 불가** | 환경 문제 — 서버 다운, 시뮬레이터·개발 서버 미기동, 로그인 만료, 권한 없음 | 통과도 실패도 아니다. 무엇이 막혔는지와 필요한 조치를 보고한다 |

증거가 없는 항목은 통과가 아니라 **미검증**이다. 보고서에 그대로 남긴다.

### 실패했을 때

1. **먼저 분류한다.** 같은 입력으로 한 번 더 돌려 재현되는지 본다. 이때 아무것도 바꾸지 않는다
2. 재현되면 실패, 결과가 달라지면 불안정, 실행 자체가 막히면 검증 불가로 판정한다
3. 실패는 원인 가설을 세우고 고친 뒤 다시 검증한다
4. **같은 원인으로 수정을 두 번 했는데도 결과가 달라지지 않으면 멈추고 보고한다.** 아무것도 바꾸지 않고 다시 돌리는 건 수정 횟수에 넣지 않는다. 그건 재시도일 뿐이다
5. 기준선에서 이미 실패하던 테스트는 이번 변경의 실패로 세지 않는다. 대신 보고서에 "기존 실패"로 적는다

## 5. 보고서

`/feature` 체크포인트 2, 또는 검증을 요청받았을 때 이 형식으로 보고한다.

```markdown
### 검증 — L2 (근거: 공용 Avatar 수정, 사용처 4곳)

| 항목 | 판정 | 증거 |
|---|---|---|
| 프로필 사진 변경 시 미리보기 갱신 | ✅ | `ProfileEditor.test.tsx` "사진을 고르면 미리보기가 바뀐다" |
| 업로드 실패 시 이전 사진 유지 | ✅ | 같은 파일 "업로드 실패 시 이전 사진을 유지한다" |
| 계정 화면 (변경 전/후) | ✅ | 캡처 2장 — 뱃지 위치·크기 시안과 일치 |
| 댓글 목록 프로필 (이어진 기능) | ⏸️ | 개발 서버 API 다운 (502). 서버 복구 후 확인 필요 |

- 타입에러: 기준선 12 → 12
- 린트: 변경 파일 위반 0
- 기존 실패: `Legacy.test.tsx` 1건 (이번 변경과 무관, 기준선부터 실패)
- 미검증: 댓글 목록 프로필 — 위 사유
```

미검증·불안정·검증 불가 항목이 하나라도 있으면 **요약 첫 줄에 밝힌다.** 표 아래에 묻어 두지 않는다.
