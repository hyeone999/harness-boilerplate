# 명세 ↔ 구현 크로스체크

## 입력

- 기능명세서: 텍스트 또는 링크
- Figma 링크면 MCP의 `get_screenshot`으로 이미지를 받아 읽는다

## 절차

### 1. 명세를 항목으로 분해한다

각 문장을 **검증 가능한 단위**로 쪼갠다.

❌ "랭킹 화면 구현"

✅

- 순위 노출
- 순위변동 노출 (▲▼/NEW)
- 썸네일 노출
- 제목 노출
- 별점 노출
- 카드 탭 시 상세 화면 이동

분해한 항목명은 그대로 테스트 이름이 된다 (`test-strategy` 참고).

### 2. 항목마다 3단계로 확인한다

| 단계 | 확인 내용 | 방법 |
|---|---|---|
| 코드 존재 | 해당 로직이 있는가 | `grep` |
| 배선 | 호출부·렌더 지점이 있는가 | `grep`으로 사용처 확인 |
| 데이터 | API가 값을 주는가 | `{설정:API 스키마}` 확인 (없으면 MSW handler) |

**세 단계를 모두 봐야 한다.** 코드만 보고 판단하면 다음을 놓친다.

- 함수는 있는데 아무도 안 부른다
- UI는 있는데 서버가 값을 안 준다
- 화면은 등록됐는데 진입 경로가 없다

API 스키마는 전체를 읽지 말고 스키마명으로 좁힌다.

```bash
grep -n "    SchemaName:" -A 30 <스키마 파일>
```

### 3. 대조표를 만든다

| 명세 항목 | 구현 | 근거 | 검증 증거 |
|---|---|---|---|
| 순위변동 | ✅ | `RankingItem.tsx:40` | `RankingItem.test.tsx` "순위가 오르면 ▲를 표시한다" |
| 상세 이동 | ✅ | `RankingScreen.tsx:48` | 미검증 |
| 별점 노출 | ❌ | 응답 스키마에 평점 필드 없음 | — |

구현 상태는 세 가지만 쓴다.

- ✅ 구현됨 (코드·배선·데이터 확인)
- ⚠️ 구현됐으나 명세와 다름 (시점·조건·값)
- ❌ 미구현 또는 데이터 없음

**검증 증거** 칸은 `verify` 스킬이 채운다. 분석 단계에서는 비워 두고, 검증 후 증거가 없으면 "미검증"으로 남긴다. 구현이 ✅여도 증거가 없으면 동작을 확인한 게 아니다.

⚠️의 예: 명세상 "화면 진입 시" 보내야 할 이벤트가 실제로는 모달 확인 버튼에서 발화하던 경우.

### 4. 원인을 구분한다

❌·⚠️ 항목은 **누구의 작업인지** 밝힌다.

- 클라이언트 미구현 → 우리 작업
- API 필드 없음 → 백엔드 요청 (그동안은 MSW로 진행할지 개발자에게 묻는다)
- 명세가 기술적으로 불가 → 명세 수정 요청

이 구분이 없으면 대조표를 받고도 다음 행동을 정할 수 없다.

### 5. 명세에 없는 것도 본다

두 방향으로 본다.

**이어진 기능 — 이 변경과 연결된 기능은 무엇인가**

모든 화면을 훑는 게 아니라, 이 기능에 이어진 기능을 떠올린다.

- 이 데이터를 **또 어디서 보여주나** — 프로필 사진을 바꾸면 댓글의 프로필도 바뀌어야 한다
- 이 기능의 **앞뒤 흐름**은 — 권한을 받는 곳이 늘면 온보딩 안내·거부 시 안내도 맞춰야 한다
- 서버에 **같은 값을 주는 다른 응답**이 있나 — 백엔드 요청에 함께 넣는다

떠오른 연결은 `grep`으로 사용처를 확인하고, 대조표에 "명세 외 연결"로 넣는다. 포함 여부는 사용자가 정한다.

**역방향 — 코드에는 있는데 명세에 없는 것**

누락된 문서화이거나, 불필요한 구현이다.
