# UI 검증

도구별 실행 방법은 같은 디렉터리의 `method.md`에 있다. `/setup-harness`가 프로젝트 스택에 맞는 프리셋에서 복사해 둔다. 없으면 `/setup-harness`를 먼저 실행하도록 안내한다.

이 파일은 도구와 무관한 캡처 원칙만 다룬다. 무엇을 얼마나 확인할지(레벨), 무엇을 증거로 인정할지, 실패 판정은 `verify` 스킬을 따른다.

## 가장 싼 검증부터 고른다

| 순서 | 방법 | 쓰는 경우 |
|---|---|---|
| 1 | Storybook 스토리 캡처 | 컴포넌트·화면 단위 UI. 로그인·서버 상태와 무관하게 같은 결과가 나온다 |
| 2 | 개발 서버/앱 + MSW | 여러 화면을 잇는 흐름. 데이터는 MSW로 고정한다 |
| 3 | 실제 백엔드에 붙여 확인 | API 연동 자체를 확인할 때만 |

## ⚠️ 최신 코드가 로드됐는지 먼저 확인한다

이미 떠 있는 개발 서버·앱은 **캐시된 구버전 코드로 동작할 수 있다.** 변경하지 않은 코드를 검증하고 "동작 안 한다"고 오판한 사례가 있다. `method.md`의 최신 코드 확인 절차를 먼저 밟는다.

## 레벨별로 찍을 것

| 레벨 | 캡처 |
|---|---|
| L0 | 바뀐 지점의 변경 전/후 한 쌍 |
| L1 | + 해당 상태별(기본·로딩·빈 데이터·에러) 한 장씩. Storybook이 있으면 스토리로 |
| L2 | + 진입부터 이탈까지 시나리오의 주요 단계, 이어진 기능의 사용처마다 한 장 |
| L3 | + 실서버·실기기에서 핵심 플로우 |

캡처마다 **비교 대상(시안 또는 변경 전)과 무엇을 확인했는지 한 줄**을 붙인다. 이게 없으면 증거로 인정하지 않는다 (`verify` 3번).

변경 전 캡처는 코드를 고치기 전에 찍는다. 이미 고쳤으면 `git stash` 후 찍고 되돌린다.

시나리오가 실패하면 `verify`의 판정 절차(실패·불안정·검증 불가)를 따른다. 스크린샷으로 화면이 맞는지 먼저 보고, 시나리오 자체의 문제는 따로 처리한다.

## 시나리오는 짧게 쪼갠다

한 시나리오에 화면을 길게 이어붙이면 앞 단계가 흔들릴 때 뒤가 전부 죽는다. 화면·관심사 단위로 나눈다.

시나리오는 **작업마다 그때 만든다.** 미리 다 만들어두지 않는다.

- 요소는 접근성 역할·고정 텍스트로 찾고, 없을 때만 `testID`/`data-testid`를 쓴다
- 사용자 데이터처럼 **바뀌는 값으로 찾지 않는다**
- 단계마다 도달을 확인한 뒤 스크린샷을 찍는다
- 캡처만을 위해 추가한 `testID`는 PR을 올린 뒤 제거한다

## 판독

스크린샷은 스크래치패드에 두고 Read로 열어 판독한다. 디자인 시안이 있으면 나란히 비교한다. 대화에는 판독 결과만 가져온다.

## 한계

소셜 로그인처럼 외부 앱·브라우저를 거치는 단계는 자동화하지 않는다. 로그인된 상태를 전제로 하고, 세션이 만료되면 사용자에게 로그인을 요청한다.

## 요소를 못 찾을 때

판정 전에 다음을 의심한다.

1. 최신 코드가 아님 (위 확인 절차)
2. 화면이 아직 로딩 중 — 대기가 필요한지 확인
3. 텍스트가 데이터에 따라 바뀜 — 접근성 역할이나 `testID`로 교체
