# 테스트 전략

도구는 `CLAUDE.md` 하네스 설정의 `{설정:테스트 도구}`를 따른다. 기본 조합은 다음과 같다.

| 층 | 웹 | React Native |
|---|---|---|
| UI 상태 | Storybook | (선택) Storybook RN |
| 통합·단위 | Jest(Next) 또는 Vitest(Vite) + Testing Library | Jest + React Native Testing Library |
| E2E | Playwright (CI) | Maestro |
| 네트워크 모킹 | MSW | MSW (`msw/native`) |

## 트로피 — 통합 테스트가 중심이다

단위 테스트를 많이 쌓지 않는다. **사용자가 하는 행동 단위로 화면·훅·API 호출을 함께 묶어 검증한다.**

```
      E2E         핵심 플로우 몇 개만 (CI)
  ───────────
   통합 테스트     ← 대부분 여기
  ───────────
    단위 테스트     순수 함수·계산 로직만
  ───────────
   정적 분석       타입체크·lint
```

단위 테스트는 **입력과 출력만 있는 순수 로직**(금액 계산, 날짜 포맷, 파서)에만 쓴다. 컴포넌트 내부 state나 훅의 구현 세부를 직접 테스트하지 않는다. 리팩터링할 때마다 깨지고, 깨져도 사용자 영향이 없다.

## 레벨별로 쓸 테스트

검증 레벨은 `verify` 스킬이 정한다.

| 레벨 | 테스트 |
|---|---|
| L0 | 새로 쓰지 않는다. 기존 테스트가 깨지지 않는지만 본다 |
| L1 | 바뀐 컴포넌트의 통합 테스트: 성공 1 + 실패 1 (에러·빈 데이터) |
| L2 | + 화면 흐름 통합 테스트 + 이어진 기능 쪽 기존 테스트 전체 실행 |
| L3 | + 핵심 플로우 E2E |

## 좋은 테스트의 세 가지 기준

### 1. 핵심 기능이 성공하는가

명세의 핵심 시나리오부터 쓴다. "등록 버튼을 누르면 목록에 새 항목이 보인다"처럼 **사용자가 보는 결과**를 단언한다.

- 쿼리는 `getByRole`·`getByText`·`getByLabelText` 우선. `testID`/`data-testid`는 대안이 없을 때만
- 성공 경로 1개 + 실패 경로(서버 에러, 빈 데이터) 1개를 한 세트로 본다
- 커버리지 수치를 목표로 삼지 않는다

### 2. 추적이 가능한가

테스트가 실패하면 **어떤 명세 항목이 깨졌는지, 어느 코드인지** 바로 알 수 있어야 한다.

- `describe`는 화면·기능 이름, `it`/`test`는 **명세 항목 문장**으로 쓴다. `spec-crosscheck` 대조표의 항목명과 같게 맞춘다

  ```ts
  describe("할 일 추가", () => {
    it("저장하면 목록 맨 위에 새 할 일이 보인다", ...);
    it("서버 에러면 입력값을 유지하고 에러 토스트를 띄운다", ...);
  });
  ```

- 단언 하나가 실패했을 때 메시지만으로 원인이 보이게 한다. 한 테스트에 시나리오를 여러 개 몰아넣지 않는다
- 테스트 파일은 대상 코드 옆에 둔다 (`Foo.tsx` ↔ `Foo.test.tsx`)

### 3. 독립적인가

- 테스트 간 상태를 공유하지 않는다. 실행 순서를 바꿔도, 하나만 돌려도 통과해야 한다
- 전역 store·쿼리 캐시는 테스트마다 새로 만든다 (`new QueryClient()`를 `beforeEach`에서)
- 시간·랜덤·네트워크를 고정한다 (fake timers, 시드, MSW)
- 실제 백엔드·외부 API를 부르지 않는다

## 모킹 — 백엔드가 붙기 전에는 MSW

**네트워크 경계에서만 모킹한다.** `fetch`·axios·API 함수를 `jest.mock`으로 갈아끼우지 않는다. 요청 URL·헤더·직렬화까지 실제 코드가 그대로 돌아야 통합 테스트의 의미가 있다.

handler는 한 벌만 두고 모든 곳에서 함께 쓴다.

```
{설정:아키텍처 → mocks 위치}/
├── handlers/          도메인별 handler (API 스키마의 요청·응답 타입을 그대로 쓴다)
├── fixtures/          응답 예시 데이터
├── browser.ts         개발 서버·Storybook용 (setupWorker)
└── server.ts          Jest·Vitest용 (setupServer)
```

| 쓰는 곳 | 방법 |
|---|---|
| 개발 서버 | `{설정:모킹 스위치}` 환경변수가 켜져 있을 때만 `worker.start()` |
| Storybook | `msw-storybook-addon`으로 스토리별 handler 지정 |
| Jest·Vitest | `server.listen()` / `resetHandlers()` / `close()`를 setup 파일에 |
| RN | `msw/native`의 `setupServer` |

### 규칙

- handler 응답은 **API 스키마 타입으로 타이핑한다.** 스키마가 바뀌면 컴파일 에러로 드러나야 한다
- 성공·에러·빈 응답을 handler 변형으로 준비해 둔다. 테스트는 `server.use(...)`로 그 테스트에만 덮어쓴다
- 아직 스키마가 없는 API를 모킹할 때는 **추정한 응답 형태를 개발자에게 확인받는다** (의사결정 규칙). 확정 전 handler에는 `// TODO: 스키마 확정 전 추정` 주석을 남긴다
- 백엔드가 붙으면 모킹 스위치만 끈다. handler는 테스트용으로 계속 쓴다
- 프로덕션 번들에 MSW가 들어가지 않게 동적 import와 환경변수로 막는다

## E2E

- 핵심 사용자 플로우만 (로그인 → 핵심 기능 → 결과 확인). 화면마다 쓰지 않는다
- 웹은 Playwright를 **CI에서** 돌린다. 공식 이미지(`mcr.microsoft.com/playwright:v<버전>`)를 `@playwright/test`와 같은 버전으로 고정한다
- E2E도 MSW 또는 테스트 전용 백엔드에 붙여 데이터를 고정한다. 공유 개발 서버 데이터에 기대지 않는다

## 리뷰에서 보는 것

- 새 기능에 핵심 시나리오 통합 테스트가 있는가
- 테스트 이름이 명세 항목과 대응되는가
- 구현 세부(내부 state, 호출 횟수만)를 단언하고 있지 않은가
- 테스트끼리 상태를 공유하지 않는가
- 네트워크를 모듈 mock이 아니라 MSW로 막았는가
