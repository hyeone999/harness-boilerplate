# /feature

프로젝트 값(기본 브랜치, 명령어, 폴더 역할, 리뷰어 등)은 `CLAUDE.md`의 **하네스 설정** 절을 따른다. 아래에서 `{설정:항목}`으로 표기한 값이다. 설정 절이 없으면 먼저 `/setup-harness`를 실행하도록 안내하고 멈춘다.

## 우선순위

지시가 충돌하면 이 순서를 따른다. **어느 쪽을 따랐는지 밝힌다.**

1. 사용자의 직접 지시
2. 팀 룰 (CLAUDE.md, 이 커맨드, 프로젝트 컨벤션)
3. 플러그인·외부 스킬
4. 기본 동작

플러그인은 일반적인 상황을 가정해 만들어졌고, 팀 룰은 이 코드베이스의 사정을 반영한 것이다.

## 의사결정

**스스로 결정하지 않는다.** 결정이 필요한 지점이 나오면 작업을 멈추고 개발자에게 묻는다. 답을 받기 전에는 그 결정에 기대는 작업을 진행하지 않는다.

결정에 해당하는 것:

- 명세·시안에 없거나 해석이 둘 이상 갈리는 동작·문구·디자인
- 기존 화면의 모양이나 동작이 달라지는 변경 (예: 아이콘을 공용 아이콘으로 바꾸면서 모양이 달라짐)
- 새 에셋·컴포넌트·라이브러리 추가, 작업 범위 밖 파일 수정
- 서버 응답 필드나 값을 추정해야 하는 경우

질문할 때는 선택지와 각 선택지의 결과를 함께 제시한다. 권장안이 있으면 근거와 함께 밝히되, 고르지는 않는다. 개발자가 내린 결정은 이슈 코멘트에 남긴다.

## 컨텍스트·토큰

작업을 작은 단위로 나눠 필요한 것만 주입한다.

- 파일 전체를 읽지 않는다. 파일명(`store.ts`, `api` 접두사)이나 함수(`create(`)로 좁혀 찾고 그 구간만 읽는다
- 이미 읽은 파일·구간은 다시 읽지 않는다. 같은 파일이 컨텍스트에 두 번 들어가지 않게 한다
- API 스키마처럼 큰 파일은 스키마명으로 좁힌다 (수만 줄을 통째로 읽지 않는다)
- 작업 항목 하나를 끝내고 다음 항목에 필요한 파일을 읽는다. 미리 한꺼번에 읽어 두지 않는다
- 독립적인 검사는 한 번에 묶어 실행한다
- 출력이 긴 명령은 `grep -c`, `tail`, `--name-only`로 줄인다
- 로그·스크린샷은 스크래치패드에 두고 요약만 대화로 가져온다
- 편집 후 확인용 재읽기를 하지 않는다 (편집 실패는 도구가 알려준다)

300줄 넘는 파일을 범위 없이 읽으면 hook(`.claude/hooks/limit-large-read.sh`)이 막는다.

여러 디렉터리를 훑어야 하는 탐색은 `Explore` 에이전트에 맡기고 결론(파일:줄)만 받는다. 위치를 이미 알면 직접 읽는다.

**에이전트 병렬은 서로 독립적인 작업에만 쓴다.** 같은 파일을 고치거나 한 작업의 결과가 다른 작업의 입력이 되면 순서대로 한다. 병렬로 돌리면 검토 집중력이 분산된다.

## 문체

`{설정:문체}`를 따른다. 정해져 있지 않으면 이슈·PR 본문은 `~해요` 체, 커밋 메시지와 `docs/` 문서는 평서문(`~한다`)으로 쓴다. 한 문서 안에서 섞어 쓰지 않는다.

## 절차

### 1. 입력 수집

없으면 요청한다.

- 기능명세서 (텍스트 또는 링크)
- 디자인 링크 (`{설정:디자인 소스}`)

Figma라면 MCP의 `get_screenshot`으로 읽는다. 노드 구조가 필요할 때만 `get_metadata`를 쓴다.

### 2. 분석

`spec-crosscheck` 스킬로 명세를 항목 단위로 분해한다.

함께 확인한다.

- 재사용 가능한 기존 컴포넌트·에셋 (`{설정:아키텍처}`의 공용 컴포넌트·아이콘 위치)
- 영향받는 파일
- 관련 API 스키마 (`{설정:API 스키마}`). 백엔드가 아직 없으면 MSW handler로 진행할지, 응답 형태를 어떻게 가정할지 체크포인트 1에서 묻는다 (`test-strategy`)
- **검증 레벨 (L0~L3)** — `verify` 스킬 1번 기준으로 영향 범위·위험도를 보고 제안한다
- **이어진 기능** — 이 변경과 연결된 기능을 떠올리고 사용처를 확인한다 (`spec-crosscheck` 5번)

명세는 바뀌는 화면만 적는다. 이어진 기능은 적혀 있지 않아도 함께 바뀌어야 하는 경우가 많다. 프로필 사진 변경 명세에 계정 설정 화면만 있었지만, 댓글 목록도 같은 프로필 이미지를 그리고 있었던 사례가 있다.

**작업 항목이 8개를 넘거나 영향 파일이 15개를 넘으면 분할을 제안한다.** 한 번의 `/feature`는 한 세션에서 끝나는 크기를 목표로 한다.

### 3. 🛑 체크포인트 1

다음을 제시하고 승인을 받는다.

- 명세 해석 (분해한 작업 항목)
- 구현 범위와 영향 파일
- 재사용할 기존 컴포넌트·아이콘 / 정말 없어서 새로 만들 것
- 검증 레벨과 근거, 그 레벨에서 모을 증거 (개발자가 확정한다)
- 명세에 없지만 이어진 기능 (포함할지 사용자가 정한다)
- 이슈 본문 초안
- 브랜치명

**승인 없이 다음으로 넘어가지 않는다.** 여기서 방향이 틀리면 되돌리는 비용이 가장 작다.

### 4. 이슈·브랜치 생성

```bash
gh issue create --title "<제목>" --body-file <파일> --assignee @me
git fetch origin -q && git checkout -b <브랜치명> origin/{설정:기본 브랜치}
```

브랜치를 만든 직후, 코드를 고치기 전에 `verify` 2번의 **기준선**(타입에러 수, 기존 실패 테스트, 변경 전 캡처)을 잰다.

이슈 본문:

```markdown
## 배경
<1~2줄>

## 작업 항목
- [ ] <분해한 항목>

## 참고
- 명세: <링크>
- 디자인: <링크>
```

### 5. 구현

작업 항목을 하나씩 처리한다. **항목을 마칠 때마다 이슈 체크박스를 갱신한다.**

```bash
gh issue edit <N> --body-file <갱신된 파일>
```

대화 컨텍스트에만 진행 상황을 두지 않는다. 세션이 끊기거나 컨텍스트가 압축돼도 이슈만 보면 복구된다.

결정이 필요하면 [의사결정](#의사결정)에 따라 멈추고 묻는다. 받은 결정은 이슈 코멘트에 남긴다.

### 6. 검증

`verify` 스킬로 확정된 레벨의 증거를 모은다.

- 타입체크·린트는 기준선과 비교한다. 린트는 변경 파일만 대상으로 한다

  ```bash
  { git diff --name-only origin/{설정:기본 브랜치}...HEAD; git diff --name-only; git diff --cached --name-only; } \
    | sort -u | grep -E '{설정:소스 확장자}' > "$TMPDIR/changed.txt"
  ```

- 테스트는 `test-strategy`의 레벨별 표대로 작성·실행한다. 테스트 이름은 명세 항목과 맞춘다
- 화면은 `ui-verify`의 레벨별 캡처 표대로 찍는다
- `spec-crosscheck` 대조표의 **검증 증거** 칸을 채운다

실패하면 `verify` 4번에 따라 실패·불안정·검증 불가로 먼저 분류한다. 같은 원인으로 두 번 고쳐도 결과가 달라지지 않으면 멈추고 보고한다.

### 7. 리뷰

`code-review-rules` 스킬로 리뷰한다.

지적이 나오면 수정하고 **6번부터 다시 실행한다.** 수정 후 검증을 건너뛰지 않는다.

### 8. 🛑 체크포인트 2

다음을 제시하고 승인을 받는다.

- 변경 요약
- 검증 보고서 (`verify` 5번 형식). 미검증·불안정·검증 불가 항목은 첫 줄에 밝힌다
- 리뷰 지적과 처리 내역
- 커밋 메시지 초안

### 9. 커밋·푸시·PR

승인 후 `github-pr` 스킬로 커밋·푸시·PR 생성을 진행한다. 체크포인트 2의 승인이 커밋 승인을 겸한다.

PR 본문 (내용 없는 섹션은 생략):

```markdown
Closes #N

## 구현 내용
## 화면
## 구현 중 이슈
## 리팩토링
## 테스트 방법
```

테스트 방법은 이슈의 작업 항목과 검증 절차에서 만든다. 리뷰어가 따라 할 수 있는 단계로 쓴다.

UI를 바꿨으면 **PR에 캡처를 첨부한다.** 리뷰어가 앱을 띄우지 않고도 결과를 볼 수 있어야 한다. 디자인 대조를 했다면 시안과 나란히 붙인 비교 이미지가 더 낫다.

⚠️ `gh pr edit --body-file`은 Draft 상태를 해제한다. Draft를 유지해야 하면 편집 후 `gh pr ready --undo`로 되돌린다.

⚠️ 기본 브랜치가 저장소의 default branch가 아니면 `Closes #N`으로 이슈가 자동으로 닫히지 않는다. 머지 후 직접 닫는다.

## 중단 조건

다음 상황에서는 진행하지 않고 보고한다.

- 타입에러가 기준선보다 증가
- lint 위반이 남아 있음
- 검증 판정이 실패 또는 불안정
- 확정된 레벨에 필요한 증거가 빠졌는데 이유를 댈 수 없음
- 명세 항목 중 미구현이 남아 있음
- 개발자의 결정이 필요함

**실패를 통과로 처리하지 않는다.** 실패했으면 출력과 함께 그 사실을 말한다.
